Set tandem up for this project. It exists already: it has code, and probably notes about what it is and how it is run. Tandem knows nothing of it yet. Read the project first (a README, a CLAUDE.md, a docs folder, its package.json and scripts, the layout of its code and tests, what is in its art folder if it has one), then do the three things below. Everything you make is a proposal the person accepts or rejects; make nothing up to fill a gap, and say what you could not find.

**1. Concepts.** Write down the ideas this project is already made of, as concepts: usually five to twelve. A concept is one idea a person would name when they talk about the project ("the slow burn", "rooms you walk between", "the server is never to be trusted"), not a file or a module. For each: a name, and a few sentences in plain words about what it is and what it is for, taken from what the project's own notes and code say, in the voice of those notes where there are any. Its stage says where it is: `playtest` for what is built and in use, `build` for what is half there, `design` or `idea` for what is only written about or planned. Link the ones that belong together (part-of, leads-to, clashes-with), and under what makes it real name the folders, files or tests that carry it. Propose them with concepts.create, then concepts.update for the stage, links and what makes them real. Do not write down intentions the project does not show; if you inferred something, say in the text that it is your reading.

**2. tandem.json.** This file, at the project's root, tells tandem how the project is run. If it is missing or incomplete, write it in your working copy. Its fields are all optional:
- `name`: what the project is called.
- `page`: the command that starts the project's page, with `{port}` where the port goes (tandem shows that page in a frame, and starts it a second time for your working copy on another port). If the page needs more than one thing running (a server beside it, a database), the command has to start all of it: put that in a small script in the project and name it as `sh {project}/path/to/script.sh {port}` (`{project}` is the project's own folder). Anything with a fixed port has to get one counted from `{port}` instead, or the working copy will fight the project for it. The working copy's run gets `TANDEM_COPY=1` in its environment: use it so the copy keeps its hands off whatever must not be written by unaccepted code (a real database).
- `test`: how its tests are run, as the start of a command you may run (so `node --test` lets you run one file; `npm test` only the whole suite). `check`: its type check or lint. `run`: a list of other commands you may run (a build step).
- `adapter`: only if the project already has a tandem adapter. Do not write one now; say in a sentence whether one would be worth having.
- `art`: `{ "build": "<command>" }` only if the project has drawings as text in `art/` and a step that builds them.
Take every command from the project's own scripts and notes; where the notes say how it is run on this machine (a phone, a container), follow that. You cannot start the page yourself: say plainly that the command is unrun, and what the person should see when it works.

**3. Say only what the cards do not.** The person sees every concept you proposed and every file you changed on cards beside your answer, so do not list the concepts or describe the changes again. Describe the change set once with code.describe, in a sentence. Then answer in two or three sentences: the one or two concepts you were least sure of, that the page command is unrun and what they should see when it works, and anything you could not determine. If the project has drawings in another form than tandem's, or a way to look inside it that an adapter could use, that is one more short sentence at most; do not convert or build anything for that now.
