Set tandem up for this project. It exists already: it has code, and probably notes about what it is and how it is run. Tandem knows nothing of it yet. Read the project first (a README, a CLAUDE.md, a docs folder, its package.json and scripts, the layout of its code and tests, what is in its art folder if it has one), then do the three things below. Everything you make is a proposal the person accepts or rejects; make nothing up to fill a gap, and say what you could not find.

**1. Concepts.** Write down the ideas this project is already made of, as concepts: usually five to twelve. A concept is one idea a person would name when they talk about the project ("the slow burn", "rooms you walk between", "the server is never to be trusted"), not a file or a module. For each: a name, and a few sentences in plain words about what it is and what it is for, taken from what the project's own notes and code say, in the voice of those notes where there are any. Its stage says where it is: `playtest` for what is built and in use, `build` for what is half there, `design` or `idea` for what is only written about or planned. Link the ones that belong together (part-of, leads-to, clashes-with), and under what makes it real name the folders, files or tests that carry it. Propose each with concepts.create, with its stage, links and what makes it real in the same call (a link may name a concept you proposed that still waits; concepts.update on a concept you proposed adds to its proposal). Do not write down intentions the project does not show; if you inferred something, say in the text that it is your reading.

**2. How it is run.** Tandem keeps how a project is run in its own folder inside the project (`.tandem`), never among the project's own files: the person may want tandem out of the project's history altogether. So do not write a tandem.json or a start script into the project. Propose it with `tandem run project.configure '{…}'` (project.setup shows what is there now). Its fields are all optional:
- `name`: what the project is called.
- `page`: the command that starts the project's page, with `{port}` where the port goes (tandem shows that page in a frame, and starts it a second time for your working copy on another port). If the page needs more than one thing running (a server beside it, a database), give the shell script that starts all of it as `script`: tandem keeps it as `{tandem}/page.sh`, and `page` is then `sh {tandem}/page.sh {port}`. The script is run in the project's folder (or in your working copy, for the copy's page), and `{project}` is the project's folder if you need to name it. Anything with a fixed port has to get one counted from `{port}` instead (`{port}`+1, +2: the project's page and the copy's are a hundred ports apart, so stay well under a hundred), or the working copy will fight the project for it. The same script runs for both, each in its own folder: whatever it writes while starting (a generated config, a data folder), it writes in the folder it runs in, never in `{tandem}` or `{project}`, which the two share. The working copy's run gets `TANDEM_COPY=1` in its environment: use it so the copy keeps its hands off whatever must not be written by unaccepted code (a real database).
- `test`: how its tests are run, as the start of a command you may run (so `node --test` lets you run one file; `npm test` only the whole suite). `check`: its type check or lint. `run`: a list of other commands you may run (a build step).
- `adapter`: only if the project already has a tandem adapter. Do not write one now; say in a sentence whether one would be worth having.
- `art`: `{ "build": "<command>" }` only if the project has drawings as text in `art/` and a step that builds them.
Take every command from the project's own scripts and notes; where the notes say how it is run on this machine (a phone, a container), follow that. Change the project's own files only when it cannot be run by tandem otherwise (a port that is fixed in its code), as little as that takes, and say so: that is a change to the project, and the person decides on it apart from the setup. You cannot start the page yourself: say plainly that the command is unrun, and what the person should see when it works.

**3. Say only what the cards do not, in three sentences at most.** The person sees every concept you proposed and how tandem would run the project on cards beside your answer, so do not list or describe them. Where you were unsure of a concept, say so in that concept's text ("my reading: …"), not in the chat. Your answer is one short paragraph: that it is ready to look at, that the start command is unrun and what they should see when it works, and the one thing, if any, you could not determine and need from them. Nothing about tests the project lacks, adapters or drawings unless the person asked.
